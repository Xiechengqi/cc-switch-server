# Cursor AgentService acceptance

Cursor Provider profiles remain `experimental` until OAuth and API-key credentials pass separate real-account runs. Public model discovery, forward, and Provider test are `fixture_verified`; local tests never set `live_verified`.

The normal audit has no external dependency; `node scripts/audit/audit-cursor-reference-delta.mjs --check-sources` is an optional read-only Git-object verification.
- CUR-N2 first refreshed six committed wire objects through OmniRoute `02c663cdd0e8577bdcf2b01a44046bcd46dc6a7a`. The 2026-09-28 append-only review then compared that point with `443d66996d69d7ecf887fd61158404a3cca1b192`: all 14 committed changes are dependency/lockfile, optional local embedding, test-runner, or shared stream-timing maintenance, while the six reviewed Cursor protobuf/session/executor paths remain unchanged. The conclusion stays `reviewed_no_wire_delta`, no Server production code was changed, and all 22 contemporaneous worktree entries were excluded from evidence.
- `src/proxy/providers/cursor/` is the lifecycle facade used by the shared forwarder. Cursor-specific adapter construction, model selection, native-driver dispatch, and h2 timeout mapping stay behind this boundary; the existing binding, lease, Share, attempt, terminal, usage, protobuf, and session owners are unchanged.
- `scripts/smoke/cursor-real.mjs --rail oauth|api_key` validates one rail at a time. It requires an exact Provider, Share, OAuth Account where applicable, a fresh full `*-fast` model ID, and a private schema-v2 receipt outside the repository with mode `0600`. Each receipt binds the current target commit, harness revision, Provider/runtime and Share revisions, exact OAuth identity/token generation or API-key credential generation, model, body hashes, measurements, recovery decisions, decoy counters, and secret scan. It never stores Provider/Share/Account identifiers, credentials, prompts, or raw bodies.
- Both rail validators require the selected App to appear exactly once in the Share's original `bindings`, verify that the Share's primary fields match its own unique binding, and require `enabled=true` with `status=active`. A duplicate, conflicting, or inactive Share is rejected before model-catalog access; the primary fields are not synthesized into `bindings` as an extra entry. These control-plane reads are not an atomic snapshot across APIs.
- Both rail validators require explicit nonnegative safe-integer Provider view `revision` and runtime `providerRevision`, with equal values, plus an explicit nonnegative safe-integer Share `configRevision` and a nonblank string `runtimeFingerprint`. Missing or mismatched revisions and whitespace-only fingerprints fail before model-catalog access; no fallback value is inserted into receipt scope or binding digests. This is a private evidence gate, not proof of live Cursor entitlement or an atomic control-plane snapshot.
- The OAuth validator also requires the Account control-plane projection to state `hasApiKey=false` and `needsRelogin=false` explicitly. Missing fields are not treated as false; malformed Account data is rejected before Provider or model-catalog access. This tightens private evidence validation without changing either production rail or proving live entitlement.
- The private catalog request sends optional `expectedShareId` and `expectedProviderId` query guards. The Server compares them with the Router-signed Share and its selected Provider before any catalog work; a mismatch is a conflict. Ordinary clients need neither guard, and `providerId` alone is not proof of the selected Share. OAuth's static aliases still are not entitlement evidence; API-key discovery still requires the exact credential scope and a fresh public catalog.
- The API-key validator checks the catalog's five-minute freshness when fetched and at final acceptance, then requests the signed-Share catalog again after the final Provider/Share binding recheck. Every entry in the complete dynamic catalog must have a non-empty, unpadded string ID, unique within that snapshot; the selected exact model must still appear once with `source=cursor_public_api`, `stale=false`, and a fresh timestamp. It compares a digest of the complete `data` list after deterministic ID sorting, so model additions and capability changes reject the receipt while a pure row reorder does not. This digest is not stored in the existing schema-v2 receipt; it proves only stability during one acceptance run. OAuth's static alias list is not refetched or treated as entitlement evidence. These reads are not an atomic upstream or control-plane snapshot.
- OAuth and API-key receipts must each remain within their 24-hour `recordedAt` window at final acceptance. The validator rechecks after the last Account/Provider/Share read; the API-key catalog and receipt use one acceptance time. Expiry during validation rejects that rail, without changing production wire or granting entitlement.
- The private receipt is read from one bounded read-only file descriptor before control-plane calls. Before and after reading, the validator compares device/inode, link count, size, mode, and nanosecond mtime/ctime; an ordinary same-inode in-place rewrite is rejected before any request. This does not prove an atomic snapshot against restored metadata or precisely timed concurrent writes.
- Before final acceptance, the validator resolves the configured receipt path again and compares the current file's device/inode, link count, size, mode, and nanosecond mtime/ctime with the post-read fingerprint. A replacement file or an ordinary in-place rewrite during control-plane validation rejects the rail. This final check is not atomic across APIs and the filesystem; restored metadata or a change after the check remains outside its guarantee.
- The final check also reopens the private receipt with a read-only `O_NOFOLLOW` descriptor, reads its complete original bytes (at most 1 MiB) and EOF, and compares them with the accepted snapshot while rechecking the descriptor and configured path. Adversarial OAuth/API-key fixtures with changed bytes and mocked original metadata now fail closed. The mocked metadata proves why a fingerprint alone cannot establish content; it does not imply an ordinary user can restore real `ctime`, nor does the check provide cross-API atomicity or live entitlement evidence.
- Fixture mode proves only the harness contract and records `contract_verified` / `live_pending`. OAuth success cannot satisfy API-key acceptance, nor vice versa; both contract rails remain `live_pending` until independent real receipts are reviewed.

## Typed credential contract

- Cursor OAuth may store multiple accounts. Every OAuth Provider binds one explicit Cursor OAuth account and its exact identity generation. Every API-key Provider uses one Provider-owned static key.
- A request never switches Provider, account, or key because of load, cooldown, 401, 429, quota, or network failure.
- OAuth may force-refresh the same account once after an initial 401. API key may invalidate and exchange the same key once. No committed stream is replayed.
- OAuth always uses the CLI wire rail: CLI headers, CLI RunRequest, empty RequestContext, and CLI completion policy. API key always uses the SDK wire rail: SDK headers, SDK RunRequest, rich RequestContext, and SDK completion policy. Session scope includes the rail and its protocol revision.
- Production inference defaults to authenticated `POST https://api2.cursor.sh/aiserver.v1.ServerConfigService/GetServerConfig`. The protobuf response must contain exactly one field-27 container and exactly one `agentUrl` plus `agentnUrl`; duplicates, wrong wire types, and missing values fail closed instead of inheriting protobuf first/last-wins ambiguity. Both origins must be HTTPS, default-port, pathless `api5.cursor.sh` hosts, and inference uses `agentUrl + /agent.v1.AgentService/Run`. Discovery is cached for one hour in an exact scope containing App, Provider revision, credential generation, runtime fingerprint, rail, principal, and access-token digest.
- API-key exchange defaults to `https://api2.cursor.sh/auth/exchange_user_api_key`. OAuth refresh uses the same endpoint with the bound account's refresh token as Bearer and an empty JSON body. `CC_SWITCH_CURSOR_SERVER_CONFIG_ENDPOINT`, `CC_SWITCH_CURSOR_OAUTH_AGENT_ENDPOINT`, `CC_SWITCH_CURSOR_APIKEY_AGENT_ENDPOINT`, and `CC_SWITCH_CURSOR_APIKEY_EXCHANGE_ENDPOINT` are optional complete-HTTPS overrides. Userinfo, fragments, missing paths, and non-HTTPS production URLs fail closed before credential/network work.
- A discovery 401 and an AgentService 401 share one recovery budget. The first eligible 401 may refresh or re-exchange only the same bound credential and replay once; a second 401 is terminal.
- `CC_SWITCH_CURSOR_OAUTH_AGENT_ENABLED` and `CC_SWITCH_CURSOR_APIKEY_AGENT_ENABLED` independently disable a rail. A disabled or failed rail never falls back to the other.
- Provider model-test dry-run validates the selected rail, endpoint policy, exact credential binding, request conversion, and model policy without making an outbound request. Network mode uses the normal native AgentService forwarder pinned to that Provider and requires the downstream protocol's terminal event. Test responses expose only a redacted endpoint-policy label.
- `cc-switch-server doctor` validates only rails that have enabled Cursor Provider surfaces. An invalid override or disabled runtime rail is a failing check, and diagnostics never print endpoint or credential values.

## Completion contract

- Business completion is rail-specific. API Key SDK requires `TurnEnded` or a surfaced tool call. OAuth CLI accepts those and the observed KV-after-visible-text terminal. KV without visible text never completes either rail.
- Every surfaced tool call retains one client-visible call id across pause and resume. Gemini stream and JSON responses emit that id in `functionCall.id`; a later `functionResponse.id` takes precedence, with `name` accepted only as a compatibility fallback for older clients.
- A business completion signal ends the RPC and closes the local stream immediately, matching the Cursor SDK transport; it does not wait for a later HTTP EOF or gRPC trailer.
- If the response reaches transport termination before a business completion signal, a plain HTTP/2 EOF is not sufficient: the transport must first supply `grpc-status: 0` or one valid successful Connect end-stream JSON envelope, after which the request still fails as an incomplete business response.
- Truncated protobuf, invalid UTF-8, incomplete/oversized/compressed frames, malformed or failed end-stream envelopes, data after a terminal in the same decoded frame batch, and plain EOF fail with 502 when observed before business completion.
- `TurnEnded` without text, reasoning, or a surfaced tool call is an empty failure. Non-stream requests return 502; streams emit an in-band protocol error, never a normal success terminal, and persist failed usage.

## Tool, Responses, and concurrency contract

- Client tool schemas have one semantic representation (`serde_json::Value`) across Anthropic, Chat, Responses `tools`/`additional_tools`/custom/namespace, and Gemini ingress. Only the final AgentService encoder serializes that value into `google.protobuf.Value` for `McpToolDefinition.input_schema`; UTF-8 JSON bytes are never stored as wire state. A final-RunRequest round-trip matrix enforces this invariant for both OAuth CLI and API-key SDK rails.
- Codex CLI `0.151` declares local tools under the `functions` namespace inside a Responses `additional_tools` item. The Server flattens that inventory to `functions.exec`/`functions.wait`/`functions.request_user_input` for AgentService, restores namespace metadata on output, and explicitly prefers `functions.exec` for local project work. The neutralized `codex_0151_namespaced_tools.json` fixture preserves the multiple developer/user message and environment-context shape so an earlier user item cannot hide the latest task.
- Tool declarations pass a bounded Cursor-local JSON Schema 2020-12 preflight before credentials or AgentService are opened, and the same semantic value is later used for argument validation. It supports the object/array/string/number/composition keywords used by OpenCode, Pi, and MCP tools, exact `oneOf`, and local JSON Pointer `$ref`. Non-object MCP roots, remote or recursive refs, malformed unselected branches, excessive bytes/depth/nodes/patterns, and arguments larger than 1 MiB fail closed. The Server never resolves paths or executes client tools.
- Builtin/MCP normalization is limited to fixed aliases and argument adapters. Native builtin tools match a declared alias by case-insensitive exact name (or the complete leaf of a dot-qualified Responses tool), never by arbitrary substring: for example, Cursor `Delete` cannot become a client's `undelete` or `functions.undelete`, while `functions.grep` remains a valid explicit grep leaf. An unmatched builtin keeps its typed upstream rejection. Generic SDK `mcp` wrappers may select only an exact declared client `toolName`; a supplied provider must be `providerIdentifier=client`. Routing fields may be nested under `arguments/args/input/parameters/params/targeting`, and those payload wrappers are expanded only when the wrapper key is not itself part of the target schema. A surfaced call must resolve to one declared tool and pass that tool's original schema; foreign providers, ambiguous/undeclared targets, and invalid payloads fail closed. Unknown fields are preserved when JSON Schema leaves `additionalProperties` open. Resolution exposes only low-cardinality reason metrics, not arguments or schemas.
- `tool_choice=required` and named tool choice are buffered before client business output. A prose-only turn or a different named tool is discarded and retried on the same Provider, credential generation, rail, runtime, and conversation, with three total attempts. Unconstrained `auto`, parked tool-result continuation, 429, client cancellation, and committed output are never semantically retried. Streaming clients receive the accepted attempt as a buffered SSE sequence.
- Explicit tool selection is validated before credential acquisition and AgentService dispatch. A malformed named selector cannot silently become `auto`: OpenAI Chat/Responses function names and Anthropic `type=tool` names must be non-empty strings; Gemini `ANY` accepts at most one non-empty `allowedFunctionNames` entry because the local constraint cannot enforce a wider subset without broadening it. Unknown selector kinds, malformed Gemini mode/list types, and conflicting nested/flat OpenAI names fail locally with a fixed error that does not echo client content. Valid single-name, `none`, `required`, and `auto` choices retain their existing meanings.
- A plain-language local project task (for example, `深入解读当前项目`) also enables the buffered semantic constraint even when Codex sends `tool_choice=auto`. Promise-only progress text is never a successful terminal: the Server rotates the upstream conversation for at most three attempts and publishes only an attempt that reaches a real client tool call, otherwise it emits `response.failed` followed by exactly one stream terminator.
- Every completed OpenAI Responses turn enters a process-local, scope-isolated continuation cache (10-minute TTL, 2,000 entries, 64 MiB total, 8 MiB/200 items per entry). This includes `store=false`: that flag controls durable/retrievable Responses resources, while the bounded in-process context exists only so Codex-style `previous_response_id` continuation can work and is never exposed through a response-management API. `previous_response_id` expands normalized prior input/output into a new h2 run. Restart, expiry, or any scope mismatch returns `409 cursor_response_state_lost`; it never cold-starts from the response id.
- The completed-response cache accepts at most 512 bytes for both the response ID and its local conversation ID, and charges their retained identity bytes to the entry/total capacity. Oversized IDs are not cached; this affects only local continuation state, not Cursor's outgoing protobuf.
- Parked tool continuation remains separate from completed Responses state. Anthropic, Chat, Gemini, and Responses deltas that contain only tool output resume the exact original h2 stream; missing parked state returns `409 cursor_session_lost`.
- Live h2 sessions and completed Responses continuation use exact credential-scoped identities. OAuth scope includes the managed Account instance and a domain-separated digest of the normalized access token, Cursor machine/config identity, refresh/ID token, token type, extra headers, expiry, and relogin state; API-key session scope includes the actual key digest even when the verified account id is unchanged. Same-generation credential changes therefore cannot reuse an old parked stream or completed response. Acquisition and stream opening recheck the current scope; a same-binding 401 refresh rekeys the new stream, and successful Responses state is cached under the post-refresh scope. Conversation affinity may remain stable across refresh, but it never authorizes a state lookup without the exact session/response scope. These checks are not a cross-storage atomic transaction.
- Opaque completed-response, parked-response, and tool-call IDs are exact identities within those scopes. Empty or leading/trailing-whitespace IDs cannot alias a different cached response, parked stream, or consumed continuation claim. Tool-result validation (including explicit Gemini function-response IDs), cold-resume matching, and Responses context replay reject padded call IDs before they can be matched or deduplicated; errors do not echo the supplied ID. This is a local identity boundary, not a new Cursor wire claim.
- When Cursor emits an empty, padded, over-512-byte, or already-pending tool-call ID, the Server assigns a fresh unique client-facing ID before emitting the tool call. The pending map still retains the original `exec_msg_id`/`exec_id` for the exact upstream MCP result. Valid unique IDs stay unchanged, and the client cannot receive a call ID that its continuation path would reject or that overwrites another pending call.
- Parked response/tool-call secondary indexes retain all live candidates under the exact scoped ID. Lookup first evicts expired parked sessions, then excludes closed or expired candidates even if expiry races that sweep; a locked candidate remains conservative. A running candidate still counts toward ambiguity: a duplicate result might target that in-flight conversation, so a different parked conversation with the same ID must not be selected merely because it can currently be acquired. If two live conversations share an ID, lookup returns no owner instead of selecting the last writer; once one session closes or expires, its candidate is removed and the remaining unique owner becomes resolvable. Rebinding the same session is idempotent. Ambiguous IDs never authorize a wrong h2 resume; a cold-resumable request may still use its separate full-context path.
- A cold-resumable OpenAI Responses delta that contains matching assistant-side `function_call`/`custom_tool_call` plus output does not write the result back to the parked stream. Cursor AgentService can keep that stream alive without producing another business frame. The Server atomically acquires the exact parked owner, snapshots its bounded semantic input/call items and opaque local-task continuation state, closes it, deduplicates and merges the current output, and opens a fresh same-scope conversation. Deduplication keys on `call_id` and exact call/result semantics; it ignores only Responses item-level `id` and returned `status`, which Codex may echo even though the parked semantic snapshot does not retain them. Name, namespace, arguments/input/output, type, or any unknown-field difference still fails closed as a conflicting call. A concurrently acquired owner returns retryable `409 cursor_continuation_in_progress`; it is never interrupted. Recently consumed opaque call/response IDs remain in a scope-isolated, TTL/capacity-bounded in-memory claim set so a duplicate arriving just after live indexes are removed cannot open another run. Claims are inserted atomically after the fallible snapshot and memory reservations succeed; a full claim set rejects the entire new batch with retryable `503 cursor_continuation_claim_capacity_exhausted` before a fresh AgentService run, without evicting unexpired replay fences. The exact parked owner is closed before returning that error; failed snapshots likewise close it without falsely consuming IDs. This follows the SDK oracle's new-run context replay while retaining Server-side Provider/account/Share/rail isolation.
- A second ordinary request for the same running conversation returns `409 cursor_conversation_busy`; different conversations remain parallel.
- The process-local live h2 session registry has a default ceiling of 100. A new conversation can evict the least-recently-active parked session under the existing policy, but it never evicts a running upstream stream merely to make room. If all slots remain occupied by running sessions, admission removes the new reservation before opening AgentService and returns retryable `503 cursor_session_capacity_exhausted` with a one-second retry hint. This is a local resource boundary, not an upstream Cursor quota signal.
- Request-memory accounting for a live or parked session includes both retained conversation-key strings: one in the registry and one in the session object, plus the registry key's fixed overhead. The input plan can carry a client-supplied `previous_response_id` into a new conversation key on non-Responses compatibility paths; this is a local capacity safeguard, not an assertion about Cursor's accepted ID format. It does not change key matching, OAuth/API-key scope, protobuf, or the 100-session ceiling.
- Response/tool-call secondary lookup bindings also reserve conservative request-memory space for their copied scoped ID, conversation key, hash slot, and candidate list before insertion. If the request budget cannot hold a new binding, the request fails locally without leaving a resumable partial index; closing or expiring the session releases the charge with its other retained state. This does not infer a Cursor ID format or change the upstream protobuf.
- A parked h2 session has a five-minute idle TTL even when no later request arrives: parking arms a cancellable expiry task, and reacquiring or closing the session cancels it. Expiry rechecks the exact session entry and its latest activity before closing the stream, releasing request-memory reservations, and removing response/tool-call indexes. A renewed or running session is not closed by an older timer. Lazy expiry on lookup remains as a fallback.
- `/v1/responses/compact` is non-streaming and side-effect free. It rejects tools/background/stream, returns `object=response.compaction` with a `compaction` item, and accepts that item as later Responses input. `encrypted_content` is the OpenAI-compatible field name; this implementation does not claim server-side encryption.
- `/v1/responses/input_tokens` estimates the same canonical Cursor prompt used by the request builder. Responses include `object=response.input_tokens`, `estimated=true`, `estimation_method=cursor_canonical_prompt_characters`, and `x-cc-switch-token-count: estimated`.

## API-key verified identity

- Successful Provider validation stores only a Server-owned `cursorVerifiedIdentity`. In addition to the schema version, non-sensitive stable account id, principal source, and verification time, schema v2 may contain bounded display-only email, display name, API-key name, and normalized subscription label. Client Provider payloads cannot supply this resource metadata, and no API key or exchanged token is stored in it.
- Provider validation (`/v1/me`) and API-key model discovery (`/v1/models`) use the audited Public API profile: Bearer authentication, JSON content type, `x-cursor-client-type=sdk`, `x-cursor-client-version=composer-api-0.1.0`, and `x-ghost-mode=true`. AgentService keeps its independent `sdk-1.0.13` version contract.
- `/v1/me` display extraction follows the dashboard-compatible fields (`userEmail`, first/last name, `apiKeyName`, and membership fields). Every persisted display value is trimmed and limited to 256 characters; membership values such as `pro_plus` are normalized to labels such as `Cursor Pro+`.
- A `/v1/me` 401 is terminal and never falls back. A 403 triggers one bounded validation-only POST to the normal same-key `/auth/exchange_user_api_key` endpoint; saving is allowed only when that exchange returns a non-empty access token. The temporary token is zeroized after bounded best-effort account enrichment and never reaches Provider resources, account profiles, logs, errors, or Router descriptors. Enrichment failure does not invalidate an exchange-verified key. This fallback keeps `principalSource=api_key_fallback`, never fabricates a stable dashboard identity, and never permits cross-key or cross-Provider selection. Failed Public API/exchange diagnostics expose only bounded, redacted known JSON fields.
- `/v1/me` identity selection is `userId/id/sub/user_id`, then normalized lowercase email, then an API-key hash fallback. The verified account id seeds Cursor machine/config identity; API-key digest plus `credentialGeneration` still fences exchange tokens, endpoint discovery, live sessions, cooldown, and completed response state.
- Rotating to a key verified for the same account preserves machine/config identity while incrementing credential generation. A different verified principal returns `cc_switch_cursor_identity_conflict`; delete and recreate the Provider to perform the explicit operator-visible rebind. Fallback identities intentionally cannot remain stable across keys.
- Provider views expose the schema-v2 fields as a read-only `cursorAccount`; Share descriptors project only `accountLabel`, `accountEmail`, and `subscriptionLevel`. Server and Router cards prefer the real account/subscription over the generic `Cursor API Key` Provider name.
- Cursor API-key account data is a Provider-owned snapshot keyed by the exact Provider and `credentialGeneration`; it never creates a managed Account. Fresh data is cached for five minutes, retryable failures may retain up to one hour of explicitly stale data, and authentication failures clear the cache. Stable display identity/subscription changes are persisted to `cursorVerifiedIdentity` and therefore update Share descriptors; volatile usage remains only in the snapshot.
- Legacy Providers without schema-v2 presentation fields are enriched when their account snapshot is next loaded or refreshed. Startup performs no blocking storage migration; an asynchronous per-Provider worker, mounted cards, and the explicit `GET/POST /api/providers/:id/cursor-account?app=...` endpoint trigger the scoped refresh. The worker runs each Provider independently every 15 minutes and never selects a different Provider or key.
- Subscription and usage enrichment currently uses the Cursor dashboard Bearer surfaces `api2.cursor.sh/auth/full_stripe_profile`, `DashboardService/GetPlanInfo`, and `DashboardService/GetCurrentPeriodUsage`. These are internal interfaces, remain experimental/live-unverified, and are bounded by timeout, a 1 MiB response limit, redacted diagnostics, partial-result handling, and no cross-identity fallback.

## OAuth account presentation

- Browser login and refresh profile parsing accept Cursor dashboard fields including `userEmail`, `stripeStatus.membershipType`, and `membershipType`. The normalized membership label is persisted as the managed Account `subscriptionLevel`, while the email is persisted as the Account identity display.
- Each OAuth quota refresh also retries the bounded dashboard identity lookup. A temporary login-time profile failure can therefore recover later without recreating the Account; partial identity updates survive an independent usage failure.
- A legacy imported Account that has no usable bearer token may continue to expose its captured quota snapshot as compatibility data. This is not the main refresh path, performs no outbound request, and never upgrades the snapshot to live evidence.
- When the OAuth token already supplies a stable WorkOS subject, dashboard profile email, membership, and expiry still enrich that same Account; profile enrichment never changes the Provider's explicit account binding.
- Share descriptors project the managed Account label, email, and subscription level. Server and Router cards therefore show the subscription tier (for example `Cursor Pro+`) and the account email instead of the generic `Cursor OAuth` label when the data is available.

## Usage and streaming timing

- AgentService does not report a cache-read/cache-write token breakdown. Cursor usage therefore keeps both cache fields unknown, exports `cacheUsageObserved=false`, and never infers cache tokens from the canonical prompt estimate. Router request cards render Cache R, Cache W, and cache-hit rate as unavailable instead of observed zero.
- Cursor input/output counts are local estimates and export `usageEstimated=true`. Router labels them as estimates; input is the full canonical prompt and may include reused conversation context, so it must not be described as fresh uncached input.
- `firstTokenMs` is recorded only when a non-terminal AgentService batch produces progressive business output. Content delivered only with `TurnEnded`, KV completion, or the final writer flush has no reliable TTFT. Router TPS aggregation additionally rejects generation windows shorter than `max(100 ms, 1% of total latency)`.

## Unsupported parameters and transient retry

- Cursor is a single-candidate text rail: Chat `n != 1`, log probabilities, audio/non-text modalities, legacy functions, Responses background/hosted tools, Gemini `candidateCount != 1`, and compact stream/tools/background are explicit 400 errors. Max tokens, stop, and JSON output constraints remain prompt-enforced best effort.
- Explicit image parts on the four supported ingress protocols must be extractable. A missing or malformed image source, unsupported URL scheme, invalid inline base64, or an image in a position that the Cursor request builder cannot carry fails locally with a fixed redacted error instead of silently sending a text-only prompt. Supported references retain MIME/signature, SSRF and redirect checks. Cursor AgentService now accepts up to 12 images, each at most 16 MiB before preparation; JPEG/PNG/WebP/GIF must have readable dimensions (longest edge at most 8192, at most 25 million pixels) and decode successfully. Images are JPEG-prepared toward 100 KiB, or 256 KiB for Chat/Responses `detail=high/original`, then rejected if still over the unchanged 1 MiB wire cap. The preparation working set uses the same request memory budget; unsupported/undecodable input fails locally rather than becoming a text-only prompt.
- Generic transient 5xx/transport replay remains disabled. No production feature gate is exposed until both OAuth and API-key rails have real evidence that a new Run before first business output is idempotent for billing and agent side effects. This does not affect the exactly-once same-binding 401 recovery or the explicit required-tool semantic retry above.

## AgentService 内嵌错误（2026-10-13）

Cursor AgentService 即使返回 HTTP 200，也可能在 Connect 数据帧中给出顶层 JSON `error`，或在 Connect 终态/gRPC trailer 给出 `resource_exhausted`。Server 只解析至多 8 KiB、确有顶层错误对象或字符串的 JSON 帧；明确额度耗尽返回 429，并按现有有界重置时间仅冷却当前绑定账号，Provider 结果记为 `RateLimited`。明确请求过大且无额度线索的 `resource_exhausted` 返回 400；未知 JSON 错误用固定 502 文案，不回显上游自由文本。其他 gRPC 状态和普通传输失败仍按原规则处理，不因此启用跨账号重试。流式请求已发送的部分内容不会被伪装成成功终态；两条真实 rail 尚需独立验收。

Composer 文本若只包含 marker 格式的工具调用，而缺少可续接的 Exec/MCP 元数据，Server 仍按原有 501 失败关闭。客户端错误只说明缺少元数据，不回显上游生成的工具名；Anthropic、Chat、Responses、Gemini 四种入口使用同一固定错误来源。这不把 marker 猜成可执行工具，也不改变 AgentService protobuf 或续接状态。真实账号验收不在当前实施 goal 内，两条 rail 继续 `live_pending`。

Metrics: `cursor_tool_resolution_total`, `cursor_tool_retry_total`, `cursor_response_cache_total`, `cursor_session_conflict_total`, and `cursor_agentservice_failure_total`. Labels are fixed outcome/reason/rail/state/phase values and contain no credential, prompt, schema, tool arguments, or upstream HTML.

## Model selection contract

- Router Share resolution selects the Cursor Provider before model parsing. A `cursor:*` name can only change the wire model or mode inside that already-selected Provider; it never selects another Provider, account, key, or Share.
- Aliases are `cursor`, `cursor-agent`, `cursor-plan`, `cursor-ask`, `cursor-composer`, and `cursor-composer-fast`. Mode prefixes are `cursor:`, `cursor-agent:`, `cursor-plan:`, and `cursor-ask:`.
- Agent, Ask, and Plan encode protobuf mode values 1, 2, and 3. A trailing `-fast` normally remains the compatibility selector encoded as base `model_id` plus `fast=true`. The bounded exception is a full ID advertised by the fresh API-key `/v1/models` catalog in the exact App/Provider revision/runtime/credential generation/key-digest scope: that ID is sent verbatim with no synthesized fast parameter. OAuth aliases, stale catalogs, or another scope cannot authorize verbatim passthrough.
- An explicit Cursor alias or prefix takes precedence over a Cursor Provider's single-model default. An ordinary unprefixed request still follows the committed RuntimePlan; passthrough mode may carry a bare Cursor wire model.
- OAuth and API-key catalogs expose the aliases. API-key discovery retains a bare upstream model ID only when it does not collide, and always exposes `cursor:<id>` plus Agent/Plan/Ask namespaced variants. Duplicate aliases and collisions are removed deterministically. A successful empty API-key catalog is authoritative. Only retryable transport/429/5xx failures may use the same scope's last-known-good, and that stale evidence expires after one hour; it is never used by the inference resolver to authorize a verbatim model ID.

## Required real matrix

Cold-resume replay fence: once a response/tool-call ID has been consumed in the exact Cursor session scope, a later parked session cannot consume the same ID again before the claim expires. A batch containing one consumed ID is rejected atomically; fresh IDs in that batch are not claimed, and the acquired parked owner is closed before a new upstream run. The client receives `cursor_continuation_in_progress`; claim-capacity exhaustion remains a separate retryable 503. This local fence does not assert a new Cursor wire guarantee and does not replace OAuth/API-key real receipts.

Run every row independently for OAuth and API key: Anthropic Messages, OpenAI Chat, OpenAI Responses, and Gemini ingress; non-stream text; stream text and terminal event; Agent/Ask/Plan modes; arbitrary `-fast` model; reasoning; data-URI image; remote image; declared auto/required/named tool call; required-tool retry; invalid schema; tool result continuation; completed `previous_response_id`; `store=false`; compact; input-token estimate; client cancellation; first-frame timeout; inter-frame timeout; 401 recovery; second 401; 403; 429 with `Retry-After`; 5xx before output; disconnect after output; malformed and oversized Connect frame; invalid gzip; missing/malformed/failed Connect terminal before business completion; nonzero gRPC trailer before business completion; concurrent limit saturation; same-conversation conflict; parked/completed state after server restart; API-key rotation; alias and namespaced model discovery; collision handling; log and error redaction.

Expected invariants: 401 recovery retains the original principal; 429 and saturation never select another identity; malformed frames, gzip failures, and nonzero trailers observed before a business completion never produce a successful response; restart returns `409 cursor_session_lost` for parked tool continuation and `409 cursor_response_state_lost` for completed Responses continuation; Cursor usage records set `usageEstimated=true`; no access token, refresh token, exchange token, API key, or private runtime endpoint appears in logs or evidence.

`CC_SWITCH_SHARE_URL` 必须是 Router 暴露的 Share URL；该验收不会调用 Server 的 `15721` 推理路径。

The script exercises Anthropic, Chat, Responses, and Gemini Server ingress. Composer-api supplies the Chat/Responses SDK oracle for equivalent canonical prompts. It does not print credentials or full response bodies.

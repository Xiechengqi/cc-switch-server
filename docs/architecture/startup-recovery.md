# 启动恢复与历史用量

> 状态 **权威文档**。实现采用 SQLite v10 数据格式。启动耗时和 RSS 的量化目标仍待运行时验收。

Server 获取数据目录锁、核对租约工作区授权后，执行 schema 核对、WAL 校验和一次数据库完整性检查。历史 payload 摘要和精确额度修订以流式方式验证。已提交实例沿用当前权威库，初始化期间的域级回读只加载对应存储。

SQLite 保存持久请求历史。运行时近期缓存同时受 2,048 条和估算 8 MiB 两项上限约束，并接入现有进程保留字节预算。缓存被淘汰后，请求重试、迟到完成及 Router ACK 通过 request ID 读取持久记录。查询工作在线程池执行，最多同时运行两个历史查询，取消 HTTP 请求后正在执行的查询继续占用其并发名额直至结束。

报表逐条累加现有 Rust 指标，保留整数溢出处理和补充用量口径。详情展示采用 32 天窗口，请求分页沿用开始时间和 request ID 的倒序及现有游标。一次报表查询中的游标检查和记录读取使用同一 SQLite 读快照。普通额度按对应用户和时间窗口读取持久历史，账号周期额度按精确修订及 watermark 查询。旧 JSON/journal 数据通过索引重放修订，集中清理保留期。

启动恢复仅更新仍处于 pending 的用户请求。每批事务提交对应请求修订、精确额度、计量证据和待同步状态，中断后可继续恢复。精确额度的水位与修订校验采用有序流，运行时保存 metadata 并按需读取精确历史。近期缓存的保存接口只允许持久化对应 metadata，完整详情替换要求完整数据集。

Provider 健康更新先持久化健康存储，再发布对应状态。周期检查、手动结果、Market 试用恢复和 Share 投影通过明确的历史查询获取其证据。缓存范围与业务查询窗口分别定义。

本地必要恢复完成后绑定 HTTP 监听。Router 注册、隧道恢复和同步在后台继续处理。`/ready` 返回本地持久化状态、process ID 和 process instance ID。全局凭据或用量持久化降级会返回 503。

`startup-state.json` 位于安装根数据目录，由取得目录锁的进程写入，记录版本、进程启动标识、阶段、已处理工作量和累计耗时。阶段推进与数据库执行进度驱动更新，写入频率受限。日志同时记录阶段耗时。该文件不承载账号凭据或请求正文。

升级助手核对目标版本、替换进程及 `/ready`，并在后续版本探测中核对进程身份。普通启动总等待上限为 180 秒，实际迁移为 600 秒，支持进度的启动在 45 秒无实际进展后判定停滞。旧版回滚保留兼容探测，总等待上限为 180 秒。停止、启动和回滚使用同一任务剩余预算，总上限为 14 分钟，Router 的升级失联确认窗口为 15 分钟。

回滚前确认替换进程退出，回滚后核对原版本和实际就绪结果。首次从旧版升级时，旧版 helper 的等待策略仍然生效，需覆盖该兼容场景。

当前数据规模的拟定运行时验收目标为约 248 MB 数据库、3.8 万条记录下本地就绪不超过 15 秒、空闲 RSS 低于 512 MiB、初始化峰值低于 768 MiB。逻辑字节预算与操作系统 RSS 分别采集。静态编译和契约审计提供代码层面的验证，性能与 OOM 分配来源需要运行时采样。
